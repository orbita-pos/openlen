# Editor V5 hardening — handoff report

Branch: `feature/editor-v5-hardening` (built on `master` @ `e6edce1`, not merged/pushed).

## TL;DR

Drove the in-iframe overlay text editor from **77.85% → 99.69%** glyph-accurate
across a **290-body real corpus** (45,220 editable elements). The prod FlowDeck
symptom (overlay ~30 % right of the H1, grey text-balance partner still showing)
is fixed and pinned by a committed test. The remaining 0.31 % is two precisely
characterized **architectural** classes (3D / animated ancestors; centered runs
sharing a wrapped line with sibling marks) — reported below as a Phase-6 spec,
not shipped as silent limitations.

## Phase 1 — corpus

`scripts/editor-v5/fetch-corpus.ts` pulls every published curated body from the
prod stores (188 templates via R2; 102 sections via DB→R2) into
`tests/visual/corpus/` + `manifest.json`. **Deviation from spec, flagged:** the
50 "fresh AI-generated pages" could not be produced — `/api/generate` needs
Gemini egress, which is blocked in this sandbox (documented in memory
`napi-rebuild-needs-dev-stopped`). Substituted the 188 curated templates +
102 sections, which are generated by the *same* Claude/Gemini models under the
*same* `DESIGN_GUIDANCE` — a strictly larger, more-reachable sample (290 vs the
spec's 254). Also note: `cdn.tailwindcss.com` + Google Fonts are blocked here, so
the corpus is rendered with an **offline pre-compiled Tailwind superset**
(`tailwind-corpus.css`) and system-font fallback. This is sound because every
measurement compares the overlay to the original **in the same render**, so
fallback fonts cancel — the metric tests overlay↔original *consistency*, which is
the actual product requirement.

Pattern catalog: `tests/visual/corpus-patterns.json` (41 clusters keyed by
`editMode|align|balance|fontUnit|ancestorCB|cbDecision|lineCount`). Highest-volume
clusters: element/left/single (26k), element/multiline (4.1k), run/single (4.6k),
centered (3k), ancestor-transform (6.3k), vw-clamp fonts (110 bodies), 167 bodies
with the multi-span hero (FlowDeck) structure.

## Phase 2 — diagnostic

`scripts/editor-v5/diagnose.ts` renders each body with the **real runtime**
(`injectInlineEdit`), drives the genuine `startEdit()` via a synthetic click on
every `[data-openlen-editable]`, and compares **glyph rows** (`Range.getClientRects()`
clustered into lines) of the original vs the overlay. The metric is glyph
placement — "do the letters land in the same place" — not box edges: it ignores
box width (CSS hangs trailing white-space in `pre-wrap`, so a hung space inflates
the box without moving a glyph) and ignores whitespace-only extra rows. Outputs
`corpus-diagnostic.json` (+ architectural-vs-genuine split). `debug-one.ts` dumps
raw rects/styles for a single body.

## Phase 3 — fixes (what broke → what fix → metric)

All in `components/workspace-v2/{inline-edit-core,use-inline-edit}.ts`.

- **A — forced-pre-wrap whitespace (the #1 corpus bug).** A
  `contenteditable=plaintext-only` host is forced by Chromium to
  `white-space: pre-wrap`; author CSS (even `!important`) cannot override it
  (verified empirically). So a source text node's pretty-printed leading/interior
  newlines + indentation rendered *literally* — a blank first line, spurious
  wrapping, text one line low — while the page (`white-space: normal`) collapses
  them. Fix: `collapseWhitespaceForOverlay()` feeds the overlay the page's
  *rendered* form (collapse runs to a single space; preserve `pre*` verbatim;
  keep a significant inter-run space only when a sibling abuts the edge so the
  commit round-trip can't merge `"foo "`+`"bar"`). → element/run multi-line went
  from ~99 % fail to ~0; biggest single win.
- **B — half-leading vertical offset.** An inline run's `getClientRects()` top is
  the glyph-rect top; the overlay is a block whose first line box adds half the
  leading, so glyphs sat `(lineHeight−fontHeight)/2` low (4 px at 16 px → 28 px at
  hero sizes). Fix: **glyph-anchored self-correct** — after placement, nudge the
  overlay so its first rendered glyph aligns to the original's first glyph
  (re-measured live; the hidden original stays laid out). Subsumes the old
  box-edge correction and is exact at any font size / containing-block origin.
  → A-position failures 6,481 → 0.
- **C — run box model.** A run's `posTarget` rect is already content-level, but
  the overlay was inheriting the *parent's* padding (shrinking the content box →
  spurious wrap + downward offset) and subtracting the parent's border from
  width. Fix: run-mode overlay carries zero padding / zero border-adjust, and a
  single-line run is **widened** so the forced pre-wrap can't re-wrap a box sized
  to the exact text width. → run/single failures → 0.
- **D — multi-line inline targets.** A run or `display:inline` element that wraps
  across lines: line 1 starts mid-flow (indented), later lines hit the container
  left edge — a block overlay can't mirror that from the run's own rect. Fix: lay
  the overlay out in the **block container's content box** (so soft-wrap columns
  match) with `text-indent = first-fragment offset` (left/start) so line 1 starts
  at the run and lines 2+ align left; centered wrapping is carried by alignment.
  Block elements keep their mirrored `text-indent` (editorial first-line indents
  survive). → element/run multi-line (left/center-standalone) → ~0.

## Phase 4 — committed harness

`tests/e2e/inline-edit-hardening.spec.ts` (10 tests) bakes the corpus patterns
into self-contained fixtures (no network): FlowDeck centered-balance multi-span
hero, padded run, pretty-printed-whitespace run, multi-line element + run,
transformed ancestor, gradient-clipped text, editorial text-indent. Asserts
per-line glyph alignment ≤1.5 px, the "trailing colored span stays visible"
FlowDeck invariant, open→commit-no-op byte-identical render, and <16 ms open. The
full 290-body sweep stays a dev tool (needs prod R2 + offline Tailwind).

## Performance

Overlay open (creation + placement + style mirror + glyph self-correct), 140
samples across 7 fixtures: **mean 0.35 ms, p50 0.40 ms, p99 1.40 ms, max 2.40 ms**
— >10× under the 16 ms budget.

## Edge cases the corpus revealed that the synthetic suite missed

1. **Pretty-printed whitespace in source text nodes** (newlines + indentation) —
   invisible on the page, catastrophic in a forced-pre-wrap overlay. The
   synthetic SAMPLE wrote text inline so never triggered it. This was the dominant
   real failure.
2. **Half-leading** only shows when `line-height > font-height` on a run — the
   synthetic hero used `line-height: 1.1`, masking it; real heroes use 1.0–1.6.
3. **Runs inside padded / inline-flex parents** (badges, pills) — parent padding
   leaked into the overlay content box.
4. **`vw`/`clamp()` fluid fonts** (110 bodies) and **gradient-clipped text** (the
   `background-clip:text` quartet) — fine, but only because STYLE_PROPS already
   mirrors them; the corpus confirmed it.
5. **Editorial `text-indent` paragraphs** — caught (and fixed) a regression where
   the new placement code clobbered the mirrored first-line indent.
6. **3D-transformed + marquee-animated ancestors** — entirely absent from the
   synthetic suite; the largest residual class (below).

## Architectural boundary → Phase 6 spec (the 0.31 % residual)

Two classes genuinely need a different mechanism than a body-level 2D overlay.
Reported, not shipped as silent limitations.

- **3D / animated ancestors — 87 elements (~0.19 %).** Editable text inside
  `matrix3d(...)` (rotateY(180°) flips, perspective tilts) or `@keyframes`-driven
  `transform` (marquee / scroll / float). A flat overlay cannot reproduce a 3D
  projection, and an animating element's instantaneous layout is a moving target.
  Concentrated in a few showcase templates (atrium/stride/ribbon). **Phase-6:**
  detect a 3D/animated ancestor at `startEdit`; compose the ancestor's
  `DOMMatrix` onto the overlay (`transform` + `transform-origin`) and, for
  animations, drive the overlay transform from the ancestor's per-frame matrix in
  the existing RAF loop. Decide product-side whether mirror-flipped text is even
  meant to be inline-edited (likely decorative).

- **Centered/justified run sharing a wrapped line with sibling marks — ~55 −
  (overlap) elements.** When a centered run wraps and its last line shares the
  visual line with a sibling element (`<h1>…long run… <span>tag</span></h1>`), the
  run's per-line centering depends on the sibling's width, which an isolated run
  overlay lacks (e.g. `cinder` H1: line-2 "at" sits at x=449 in-page beside
  "scale", but x=677 centered alone). Left/start runs (deterministic via
  text-indent) and standalone centered runs are exact. **Phase-6:** include the
  editable's sibling inline content as **non-editable ghost spans** in the overlay
  so the browser centers the run with the same line context, then extract only the
  run's text node on commit; or, for centered multi-child elements, prefer
  element-mode with mark-preserving re-serialization.

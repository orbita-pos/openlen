# OpenLen — repo-level instructions for Claude Code

OpenLen is a landing-page builder — and, since 2026-10-07, a builder of **web apps** too (see the app row of the table and invariant 6). Users describe a page (or pick a template, or paste their own HTML), edit, and publish to `<sub>.<publish host>` — the host is `PUBLISH_BASE_HOST`, and **production has been `openlen.app` since 2026-08-23** (⚠️ **only `.app` serves pages since 2026-09-10** — `61cec120` narrowed the Caddy wildcard to `*.openlen.app` and `*.openlen.com` now just 308-redirects there; this line used to say the two served the same folders, and that staleness already cost one wrong code comment. `.app` is a separate browser origin, which is the point). Never hardcode either — `lib/publish/base-host.ts` is the single source. The repo runs as a Next.js app self-hosted on Hetzner — **never Vercel**. Brand was renamed from "Inari Pages" on 2026-05-16; `Inari Watch` is a separate sister product (monitoring, not pages), don't conflate.

## Architecture invariants — do not break

1. **Templates are HTML files, not React components**. Each template is pure HTML (Tailwind CDN + Google Fonts inline) — its body lives in object storage, its metadata in Postgres. Do NOT port them to TSX — we tried, the user rejected it. Add a new one with `npm run templates:add` (see the Template gallery section); never by dropping files in the repo or editing a registry.
2. **Templates never claim subdomains**. Only user projects do, at publish time. `mirror.html` is inspiration; `<myco>.<publish host>` is what a user gets after cloning Mirror + clicking Deploy.
3. **The published DOCUMENT is static HTML**. `project.data.html` → `/var/www/openlen/<sub>/…` → **Caddy** serves it straight off disk. No React runtime and no Node in the render path; Tailwind via CDN is OK. ⚠️ **"No Node hop" is no longer absolute**: the published page calls back for the backend features — `/c/*` (analytics beacon), `/api/f/*` (form submissions), `/api/chat/*` — and `/ai/v1/*`, the AI of the apps, which a project's Edge Functions call (never the page) — which Caddy reverse-proxies to Next from inside the same wildcard block. The page RENDERS without Node; it INTERACTS with it.
4. **`publishToDir` rejects HTML containing `data-slot-path=`** — a reserved editor-mode marker. The `from-html`, `from-template`, and `ai-design` paths reject it too (defense in depth) — it must never reach disk or the DB. The OTHER editor marker, `data-op-id`, is **stripped, not rejected** (`stripOpIds`): a slot-path means the document came from a pipeline that no longer exists, while an op-id is an inert attribute on an otherwise correct page — rejecting it would punish the user for an upstream bug of ours.
5. **La terminal de Len ejecuta en una caja de E2B, nunca en la máquina de producción** (desde el 2026-10-21, `lib/agent/sandbox/`, spec local `2026-10-21-real-terminal-e2b-design.md`; `E2B_API_KEY` la enciende, `OPENLEN_SANDBOX=0` la apaga; runbook `infra/SANDBOX_RUNBOOK.md`). Con la clave, el `bash` de Len corre en una caja aislada POR PROYECTO (node, python3 con pip, red sólo a npm, PyPI, GitHub, los CDN de las páginas y las descargas CC0 de Poly Haven y ambientCG) **para los proyectos de un dueño con plan de pago**, o de una cuenta de `OPENLEN_SANDBOX_ONLY_USERS` (desde el 2026-11-05, Jesús: la caja la paga el dueño; antes, sólo la lista); el plan se lee una vez por turno en la ruta y lo siguen la descripción de `bash`, el manual y `terminalForTurn` (`ownerGetsTheBox`, `lib/agent/sandbox/config.ts`) que se pausa al acabar el turno, se cobra por segundo al dueño (superficie `sandbox` del libro de créditos) y se mata tras una semana pausada (`openlen-sandbox-reaper.timer`) o al borrar el proyecto. La copia buena sigue en Postgres: los ficheros entran por manifiesto, y lo que un comando cambia SALE por las mismas guardas que `Write` (`guardarLoDeLaTerminal` → `aplicarPlan`); lo que se niega se deshace en la caja. `git`, `gh` (con la GitHub App del dueño: el token nunca entra en la caja), `supabase`, `stripe` y, en una app, sus comprobaciones, pruebas, `npm run build` y `npm install` los sigue contestando OpenLen por un buzón de ficheros (`bridge.ts`), porque tienen que dar lo mismo que el lienzo y la publicación. 🔴 Los datos de los visitantes (`/.openlen/bandeja`, `/.openlen/resultados`) **nunca entran en la caja**: Len los lee con sus herramientas. Tampoco en un trabajo de una herramienta (`lib/tools/jobs/`): recibe sólo los ficheros de su versión, su entrada y lo que la persona eligió en el selector de OpenLen; un informe con datos de visitantes se hace en el marco y se entrega con `files.deliver`. Si la caja no está (sin clave, tope diario `OPENLEN_SANDBOX_DAILY_USD`, otro turno la tiene, no abre o se muere a media vuelta), el turno sigue con **la terminal de siempre, que interpreta y no ejecuta**, y Len lee una línea que lo dice; la del usuario (la lente Código) es siempre ésa. **La terminal de siempre** (`lib/agent/terminal/`, F1 de `plans/len-agente-2026`; encendida por defecto desde el 03/10, como en DeepSeek: sólo `OPENLEN_TERMINAL=0` apaga las dos): no crea procesos, no toca el disco del servidor ni la red; sus ficheros son los del proyecto, y todo lo que escribe entra por las mismas guardas que `Write`. Es `just-bash` en un `worker_thread`, nunca en el hilo de la app. Lo que el modelo lee de un comando es lo del `Bash` de Claude Code (desde el 2026-10-09; antes, la línea de DeepSeek `[Command finished with exit code N]`): la salida sola si no falla, `(bash completed with no output)` si no hay, y si falla —con la regla de su binario: `grep`/`find`/`diff`/`test` fallan del 2 en adelante— `Exit code N` arriba y la salida recortada por el medio a 10.000; el código va además en `exitCode` de la respuesta para la lente. Sus tiempos y su salida larga son los del `Bash` de Claude Code (plan 04 de las apps, tarea 7, leídos en su binario 2.1.293): 120 s por comando, `timeout` hasta 600 s; al pasarse, «Command timed out after 2m 0s» DELANTE de lo que alcanzó a escribir y código 143 (lo de antes del corte `just-bash` 3.6.0 lo tira; lo de `npm test` se guarda), y lo que arrancó el comando —empaquetar, Chromium— acaba con él; más de 30.000 caracteres van enteros a `/tmp/tool-results/N.txt` (no es del proyecto) y el modelo recibe `<persisted-output>` con la ruta y una vista previa. `npm test` en una app pide al hilo de la app correr las pruebas en el Chromium de los ojos, como `view_page`: la terminal sigue sin crear procesos. Cada comando queda grabado como cualquier herramienta (la llamada en la grabación, su salida en la transcripción del turno). `git` (spec local 2026-10-15) corre igual que `npm test`: lo pide la terminal y lo contesta el hilo de la app (`lib/git/`), y lo que restaura vuelve a la terminal y se guarda por las guardas de `Write`. El `bash` real con procesos es la caja de E2B de arriba (F7): nunca la máquina de producción.
6. **En una app, el compilador es la ÚNICA PUERTA de los fuentes** (`lib/apps/compilador.ts`). El lienzo (`/api/lienzo/site` → `servirRutaDeLaApp`), los ojos de Len (`view_page`, `use_page`) y la publicación (`publishToDir` → `compilarCarpeta`) usan el mismo: ninguno sirve un `.jsx` sin pasar por él, y los tres reciben el MISMO paquete (`lib/apps/bundler/`, esbuild-wasm en su hilo): la app es UN fichero en su entrada con sus fuentes y sólo lo que usa de sus paquetes; el lienzo y los ojos, con React de desarrollo y su sourcemap; la publicada, de producción y minificado. Un fuente que no compila: en el lienzo, un módulo que lanza su error con fichero y línea; a Len, un `<new-diagnostics>` en el acto (`lib/agent/compila-la-app.ts`); al publicar, **la publicación se niega** (y `publish` se lo dice a Len antes de la tarjeta). Lo que se importa sale del catálogo del proyecto o, si el catálogo no lo sirve, de npm abierto (esm.sh tras la aduana de `lib/apps/npm/gate.ts`, fijado en `/.openlen/esm-lock.json`): empaquetado igual en los tres caminos. ⚠️ Esta línea decía «no hay npm» hasta el 2026-11-05, y llevaba mal desde el 13/10. Si el empaquetador no contesta, el lienzo lo dice en un módulo que lanza y la publicación se niega. Len en una app tiene su prompt, su manual, su guía y sus herramientas (`lib/agent/modo-app.ts`): `view_page`/`use_page` llevan `screen`, `undo_last_change` deshace el turno anterior ENTERO (`lib/projects/deshacer-turno.ts`) y `publish` va sin idiomas. Una app NACE del esqueleto con el primer mensaje (`naceComo: "app"` → `lib/projects/nacer-como-app.ts`) y una página SE CONVIERTE en app en un turno (`convert_to_app`, `lib/agent/convertir-en-app.ts`: Len escribe `/src` con la página intacta y la herramienta voltea de una vez; si `/src` no compila, no convierte nada). En una app el lienzo la enseña corriendo y **no se edita a mano directo** (ni lápiz, ni soltar): el **modo Diseño** (`components/workspace-v2/design-mode/`, spec local 2026-10-11) elige un elemento, lo ajusta en un panel como el Design Mode de v0 y «Aplicar» lo manda a Len —con el fichero y la línea de cada elemento (`lib/apps/design/`; el compilador en modo desarrollo, sólo en el lienzo y los ojos) y una captura—, y no hay traducción automática.

## Template gallery — DB-backed (since 2026-05-18)

Curated templates are **not individual files in the repo**, and there is **no `components/templates/_registry.ts`** (that file was deleted). The gallery is database-backed:

- **Metadata** in Postgres — the `templates` table (`id` = slug = PK; name/family/accent/pitch/description/mode/status + storage fields).
- **HTML bodies** in object storage — R2 in prod (public via `templates.openlen.com`), a local FS fallback in dev (`public/template-objects/`, gitignored). Object path: `templates/<id>-<contentHash>.html`.
- **Server store**: `lib/templates/store.ts` — `listTemplates`, `getTemplate`, `upsertTemplate`, `getTemplateHtml`, `archiveTemplate`.
- **Client-safe types**: `lib/templates/families.ts` — `TemplateFamily` union + `TEMPLATE_FAMILY_META` (zero node imports, safe to import from client components).
- **Zod schemas**: `lib/templates/admin-schemas.ts` — shared by the admin API routes and the CLIs.
- **Public API**: `GET /api/templates`, `GET /api/templates/[id]`. The `/new` gallery reads through these (`components/workspace-v2/use-templates.ts`).
- **In-repo starter pack**: `templates/starter/` — 3 HTMLs (mirror, manuscript, counter) + `manifest.ts`, uploaded by `npm run templates:seed` so a fresh clone boots with a non-empty gallery.

**Adding a template** — run the CLI, never touch the repo:

```bash
npm run templates:add -- <file.html> --id=<slug> --name="<Name>" --family=<slug> \
  --accent=#RRGGBB --mode=<dark|light|cream> --pitch="<hook>" --description="<sentence>" --status=published
```

It validates against `admin-schemas.ts` (rejects `data-slot-path=`), uploads the HTML to storage, and upserts the DB row. Do NOT drop `.html` files into `public/templates/curated/` and do NOT create a `_registry.ts` — neither registers anything; the gallery never sees them. Other CLIs: `templates:republish` (re-upload HTML after edits/renames), `templates:count` (verify DB + storage state).

**Adding a new family** — add the slug to BOTH the `FAMILY` z.enum in `lib/templates/admin-schemas.ts` AND the `TemplateFamily` union + `TEMPLATE_FAMILY_META` in `lib/templates/families.ts`. The DB `family` column is plain `text`, so no migration.

**Design briefs** for new templates live in `docs/claude-design-prompts.md` — prompts run in claude.ai, each producing 5–6 landing-page HTMLs that are then registered via `templates:add`. Related brief files sit beside it (`claude-section-prompts.md`, `claude-layout-variant-prompts.md`, per-family design briefs and image prompts).

Community pages **are built**, just not the way this file predicted: there is no `community_templates` table. **Explore** (`/explore`, `app/api/explore/`, `lib/community/`) lists ordinary `projects` rows with `visibility = "public"` and `status = "published"`, joined to the author's `users.handle` — a published page becomes public, it does not become a template. Public profiles live at `/[handle]`, and remixing is counted on `projects.remixCount`.

**Design surface philosophy.** The three original surfaces are the **Chat tab** (open-ended AI editing), the **Content tab** (in-iframe text editing + section reorder + asset replace), and the **inspector** (`panels/properties-panel.tsx` — per-element properties + global radius/font/accent). ⚠️ **"Three places" undersells it now**: `components/workspace-v2/panels/` also holds modules, collections, site-pages, images, versions, submissions and insights panels, each a real surface.

**The Chat tab talks to `/api/agent`, not `ai-design`** — the agent graduated and is the default; `ai-design` is the opt-out. Reading the older comment at the top of `chat-panel.tsx` and believing it is a known trap.

**Who runs what — `lib/generation/model-policy.ts` IS the answer, and it is a table.** **Three** roles (`reasoner`, `visualCritic`, `agent`) — `designer` was retired on 2026-09-06 along with the four operations that had zero callers (`creative_direction`, `page_planning`, `initial_section_program`, `visual_repair`), leftovers of two deleted pipelines; a guard (`model-policy-sin-huerfanas.test.ts`) now fails if an operation in the table has no caller. Every surface names an OPERATION and the table picks the role, the model and the reasoning effort. 🔴 **Never restate a model name in this file** — that is exactly how the previous version of this line went stale and then misled a session into "reasoning" from it instead of from the code.

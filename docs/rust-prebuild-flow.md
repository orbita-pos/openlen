# Rust HTML engine — prebuild distribution

How the `@openlen/html-engine` Rust binding flows from source to consumer, across the three contexts we run in.

## Topology

```
crates/html-engine/             <- Rust source + napi-rs bindings
  src/                            (cargo workspace member)
  package.json                    name = "@openlen/html-engine", version = 0.1.0, private
  index.js                        generated by `napi build` (gitignored)
  index.d.ts                      generated by `napi build` (gitignored)
  openlen-html-engine.<triple>.node    generated by `napi build` (gitignored)

package.json (root)
  "dependencies": {
    "@openlen/html-engine": "file:./crates/html-engine"   <- workspace symlink
  }

lib/html-engine.ts              <- TS wrapper, imports from "@openlen/html-engine"
  (added F1 S6 — Option<T> → null shim layer for every napi export)
```

`npm install` at the repo root materializes `node_modules/@openlen/html-engine` as a symlink to `crates/html-engine`. The wrapper at `lib/html-engine.ts` resolves the import through that symlink — `npm install` does not run any crate scripts, and the symlink stays valid even if `index.js` doesn't exist yet (TypeScript's `tsc --noEmit` does require it, see "Local dev" below).

## Three contexts

### 1. Local dev

```bash
# One-time per fresh clone OR after touching any crates/html-engine/src/**:
cd crates/html-engine
npm install --no-audit --no-fund
npm run build              # ~3 min cold, ~30 s incremental

# Daily:
cd <repo root>
npm install                # links @openlen/html-engine into node_modules
npm run dev                # Next.js dev server picks up the binding
npx tsc --noEmit           # validates lib/html-engine.ts against index.d.ts
```

Local dev never touches the prebuild workflow. The `.node` is built in-place by `napi build --platform --release` and consumed directly through the workspace symlink.

### 2. CI

`.github/workflows/rust.yml` (unchanged from F1 S1) — builds the binding + runs Rust + Node tests on `windows-latest` + `ubuntu-latest` for every push touching the crate. No release, no artifact upload.

`.github/workflows/rust-prebuild.yml` (new in F1 S6) — only fires when a tag like `html-engine-v0.1.0` is pushed (or via `workflow_dispatch`). On fire:

1. Matrix-builds the napi binary on `windows-latest` + `ubuntu-latest`.
2. Uploads each `openlen-html-engine.<triple>.node` as a workflow artifact.
3. A separate `release` job downloads all artifacts and attaches them to a GitHub Release whose tag matches the pushed tag.

The release artifacts are the contract surface for production / Hetzner deploy — see context 3.

### 3. Production (Hetzner self-host)

Two options, both documented but the simpler one is the default today.

**Option A (default today) — build on the deployer.** The Hetzner box already runs `npm install` + `next build` at deploy time. As long as the deployer also runs `cd crates/html-engine && npm install && npm run build` before the Next.js build, the `.node` is in place and the workspace symlink picks it up. No external storage, no version pinning beyond the git SHA being deployed. Recommended for now — fewer moving parts.

**Option B (future, when scaling matters) — download the prebuild from GH Releases.** The deployer pulls the latest `html-engine-v*` tag's artifact for the host triple and drops it at `crates/html-engine/openlen-html-engine.linux-x64-gnu.node`. Skip the Rust toolchain on the deployer entirely. Recipe:

```bash
# Pin the version in env or infra/.env.production
HTML_ENGINE_VERSION="0.1.0"
TRIPLE="linux-x64-gnu"
ARTIFACT="openlen-html-engine.${TRIPLE}.node"
GH_REPO="orbita-pos/openlen"
TAG="html-engine-v${HTML_ENGINE_VERSION}"

cd crates/html-engine
curl -L -o "${ARTIFACT}" \
  "https://github.com/${GH_REPO}/releases/download/${TAG}/${ARTIFACT}"

# index.js + index.d.ts also need to be present — they are NOT in the release
# (gitignored, no source of truth outside the build). Two ways to get them:
#   - run `napi build` once at deploy time AFTER dropping the .node (fastest
#     option that avoids Rust toolchain — napi-rs reuses an existing .node and
#     just regenerates the JS wrappers);
#   - OR ship index.js + index.d.ts as additional release artifacts (out of
#     scope today — easy follow-up if Option B becomes the default).
```

The `optionalDependencies` block in `crates/html-engine/package.json` declares the per-platform sub-packages that a "real" napi-rs publish would produce (`@openlen/html-engine-win32-x64-msvc`, `@openlen/html-engine-linux-x64-gnu`). They are NOT published to npm today (the package is `private: true`). The block is in place so:

- The contract is visible — anyone reading the package.json sees which platforms are supported.
- If we ever flip to "real npm publish" (e.g. open-source the crate, push to GH Packages), the field is already correct.
- `npm install` does not fail when the optional sub-packages can't be resolved — it skips them silently, which is the documented behavior.

## Verifying the workflow without publishing

The workflow can be exercised locally without pushing a tag in two ways.

### With `act` (Docker required)

```bash
# Install act per https://github.com/nektos/act
act push -W .github/workflows/rust-prebuild.yml \
        --eventpath <(printf '{"ref":"refs/tags/html-engine-v0.0.1-test","ref_type":"tag"}\n') \
        --container-architecture linux/amd64
```

This runs the `ubuntu-latest` matrix entry locally (Windows matrix needs a real GH runner). The release job is skipped because `softprops/action-gh-release` requires the `GITHUB_TOKEN` to be live.

### With `workflow_dispatch` against a real branch (no tag yet)

GitHub UI: Actions → "html-engine-prebuild" → "Run workflow", input `tag = html-engine-v0.0.1-test`. The workflow runs end-to-end and creates a real release attached to that tag — useful as a dry run, but the tag stays attached, so use a `-test` suffix.

### YAML syntax check (no execution)

```bash
# Any YAML linter, e.g.:
npx --yes yaml-lint .github/workflows/rust-prebuild.yml
```

`actionlint` is the gold standard for action-specific syntax (`go install github.com/rhysd/actionlint/cmd/actionlint@latest`) — catches things like invalid action names, undeclared inputs, malformed `${{ }}` expressions. Not part of `npm run typecheck` because it's a Go tool.

## Releasing a new prebuild

```bash
# 1. Bump the version in crates/html-engine/package.json AND the
#    optionalDependencies block to match (keep them in lockstep).
# 2. Commit the bump.
git add crates/html-engine/package.json
git commit -m "chore(html-engine): bump to 0.1.1"

# 3. Tag and push.
git tag html-engine-v0.1.1
git push origin master html-engine-v0.1.1
```

The `rust-prebuild.yml` workflow fires on the tag push, builds + uploads, and creates the GH Release. Manual verification: visit `https://github.com/orbita-pos/openlen/releases/tag/html-engine-v0.1.1` — both `.node` files should be attached.

## Known limitations / out of scope

- **No per-platform sub-packages published to npm.** The `optionalDependencies` block declares them; they don't exist. If/when the crate is open-sourced, run `napi prepublish -t npm` to scaffold + publish.
- **`index.js` + `index.d.ts` are not in the release.** Option B above documents the workaround. If Option B ever becomes the default, include them as release artifacts and patch the deployer to skip the rebuild step.
- **No nightly / latest channel.** Every release is a pinned tag. Floating `latest` would require another workflow that updates a moving tag — easy to add when needed.
- **No checksums.** GH Releases provides downloadable URLs but no per-file checksum manifest. If supply-chain integrity becomes a concern, add a `sha256sum`-style step in the `release` job and include the manifest in the release assets.
